# 감도 전체 기능·구현·통합 상태

문서 기준일: 2026-07-29
기준 코드: `main` (`ccf849f`) + P2 통합 브랜치 `codex/p2-profile-rescue-share` (`e5a6947`)
문서 목적: 제품 기능, 실제 코드, 서버 배치, P1 화면 연결, 실기기 검증 상태를 한 문서에서 구분한다.

> 이 문서는 P2 통합 브랜치의 코어 구현까지 반영한다. 아직 `main`에 병합되지 않은 항목은
> **P2 코어 완료**로만 표기하며, P1 화면 연결·CAMP-2 재배포·실기기 반복 검증 전에는 사용자 기능
> 완료로 계산하지 않는다.

## 1. 상태 표기

| 표기 | 의미 |
|---|---|
| **사용 가능** | 현재 앱 화면에서 사용자가 흐름을 실행할 수 있음 |
| **코어 완료** | 로직·상태·API·테스트는 있으나 P1 화면 또는 제스처 연결이 남음 |
| **서버 완료** | CAMP-2 실제 모델과 공개 API 결과까지 확인됨 |
| **재검증 필요** | 코드와 화면은 있으나 최신 빌드에서 실기기 반복 판정이 남음 |
| **미구현/후순위** | 계약만 있거나 현재 범위에서 제외됨 |

`코어 완료`를 사용자 기능 완료로 계산하지 않는다. 감도의 Done 기준은 화면 연결과 실기기 흐름 완료다.

## 2. 최종 제품 흐름

```text
최초 실행
→ 취향 카드 5장 이상 선택
→ (선택) 카드 추가 선택 또는 좋아하는 사진으로 상황별 감도 정교화
→ 카메라가 홈
→ 자동 구도 / 영역 선택 / 기본 프레임 / 내 감도 중 선택
→ 고정된 시각 가이드에 사용자가 직접 맞춰 촬영
→ 앨범에서 현재 내 감도 결과·원본·6종 필터 비교
→ 필요하면 기억 보존 / 감도 적용 / 다시 찍었다면 중 사진 살리기 선택
→ 결과 비교 후 새 파일 저장
```

서버는 레퍼런스 분석과 사용자가 명시적으로 실행한 생성 편집에만 사용한다. 라이브 카메라 프레임은 서버로 보내지 않는다.

### 2.1 제품 경험 기준과 현재 구현의 차이

감도의 1차 가치는 여러 AI 도구를 고르는 일이 아니라, 사용자가 온보딩 카드나 레퍼런스 사진으로
정한 **내 감도**가 촬영·앨범 사진에 자연스럽게 기본 적용되는 것이다. 예를 들어 따뜻한 역광,
어두운 실루엣, 낮은 대비의 핀터레스트 사진을 취향으로 골랐다면, 사용자는 매번 필터·강도·작업을
고르지 않고도 그 방향의 보정 결과를 먼저 봐야 한다.

현재 구현은 이 기준에 아직 미달한다.

| 기대 경험 | 현재 구현 사실 | 상태 |
|---|---|---|
| 촬영·앨범 진입 시 내 감도 결과를 기본으로 제시 | 원본과 시스템 필터를 먼저 보여주며, 내 감도는 별도 필터 항목으로 선택한다 | 미구현 |
| 레퍼런스의 분위기를 사진에 일관되게 재현 | 팔레트·색온도·노출·대비 등 `ColorParams` 변환 경로는 있으나, 실제 사진군 품질 평가는 없다 | 재검증·품질 개선 필요 |
| 망한 사진만 별도의 AI 복구로 보완 | `AI로 보정`은 존재하지만 추천·선택·실행 단계가 길고 실기기에서 생성 결과 흐름이 불안정하다고 보고됐다 | 사용성 블로커 |
| 보는 위치 변경을 사용자가 의도대로 제어 | 서버 operation은 방향·강도 파라미터를 지원하지만 현재 앱 화면은 이를 명확한 선택 UI로 제공하지 않는다 | 미연결 |

따라서 AI 3의 객체 삭제·여백·시점·조명 기능은 **내 감도 기본 보정의 대체재가 아닌 2차 사진
살리기 도구**로 취급한다. 생성 후보는 사용자가 명시적으로 실행할 때만 만들며, 준비되지 않았거나
실기기에서 실패한 작업은 버튼으로 노출하지 않는다.

### 3.1 상황별 감도 프로필 — P2 통합 브랜치 추가

| 기능 | 구현 상태 | 사용자 상태 | P2 코드·연결 정보 |
|---|---|---|---|
| 버전 2 감도 프로필 | P2 코어 완료 | P1 화면 연결 필요 | `data/GamdoProfile.kt`의 `GamdoProfileV2`, 기존 `style_profile.subject_prefs_json` 사용 |
| 상황별 촬영 정책 | P2 코어 완료 | P1 연결 필요 | `SceneContextResolver`, `GamdoPolicy`, `toCameraStyleTarget()` |
| 적응형 카드 묶음 | P2 코어 완료 | P1 UI 필요 | `CardRecommendationEngine`, 12 → 12 → 최대 8장, 총 32장 이하 |
| 좋아하는 사진 기반 정교화 | P2 코어 완료 | P1 Picker·상태 UI 필요 | `ProfileRefinementRepository.refineFromPhotos()`, 최대 20장·동시 2개 분석 |
| 기존 온보딩 호환 저장 | 구현 | 사용 가능 | `ProfileRepository.saveInitialProfile()`이 V2와 기존 JSON 필드를 함께 갱신 |

- `GamdoProfileV2`는 전역 정책과 `GENERAL`, `NIGHT_PERSON`, `PORTRAIT_CLOSEUP`,
  `OUTDOOR_FULL_BODY`, `CAFE_FOOD`, `GROUP`, `LANDSCAPE`별 정책을 함께 가진다.
- 정책은 줌·피사체 비중·앵커·카메라 높이·플래시·여백·기울기·포즈 성향과 색감 파라미터를
  포함한다. 불확실하면 항상 `GENERAL`로 축소한다.
- P1은 기술 수치·신뢰도를 노출하지 않고, `야간 인물`·`카페` 등 사용자 언어의 선택 흐름만
  제공한다. 카드 데이터 제공 계약은 `docs/P1_감도프로필_카드데이터_요청.md`를 따른다.

### 5.2 탐색 우선순위

```text
REFERENCE > MANUAL > POLYGON > TAP > DEFAULT
```

- 레퍼런스 구도와 수동 프레임은 즉시 고정한다.
- 영역·탭·기본 자동 탐색은 객체가 안정화될 때까지 `Searching`을 유지한다.
- 임의 고정 레이아웃 fallback은 현재 넣지 않는다.
- 모든 상태에서 셔터는 사용할 수 있다.

### 5.3 드래그 영역 선택

P2 코어 상태: **완료**
P1 화면 상태: **버튼·제스처 연결 필요**

```text
영역 선택 버튼 탭
→ 영역 선택 모드
→ 원하는 물체를 한 번의 경로로 감쌈
→ 손을 떼면 경로 자동 닫힘
→ 영역 내부 객체 3/5 안정화
→ 고정 레이아웃
```

- 영역 선택 버튼을 누르지 않은 상태의 드래그는 선택으로 처리하지 않는다.
- `ScenePolygonRegion`은 프리뷰 픽셀을 분석 좌표로 변환한다.
- 2% 미만·80% 초과 영역은 거부한다.
- 객체 중심이 내부에 있거나 객체 박스의 35% 이상이 겹치면 후보로 인정한다.
- 취소는 `cancelPolygonSearch()`, 실행은 `rescanInPolygon(points, geometry)`다.
- 선택 밖 얼굴·물체·배경 장비는 레이아웃 후보에서 제외한다.

## 6. AI 2 — 원하는 사진으로 내 감도 만들기

| 단계 | 구현 상태 | 사용자 상태 | 비고 |
|---|---|---|---|

| SHA-256·동일 사진 캐시 | 구현 | 사용 가능 | v3 캐시는 네트워크 0회 |
| EXIF 방향·축소·메타 제거 | 구현 | 사용 가능 | 업로드 임시 파일 삭제 |

| 구도·색감·둘 다 선택 | 구현 | 사용 가능 | `ReferenceScope` |
| 활성 레퍼런스 1개 | 구현 | 사용 가능 | 교체·삭제·재실행 복원 |
| 레퍼런스 구도 우선 적용 | 코어 완료 | 재검증 필요 | AI 1 자동 탐색보다 우선 |
| 원본 반투명 오버레이 | 구현 | 사용 가능 | 0~60%, 기본 30% |
| 투명도 버튼 디자인 개선 | 미반영 | P1 연결 필요 | 용도가 보이는 아이콘·팝업 필요 |

| 내 감도를 결과 화면의 기본값으로 자동 적용 | P2 코어 완료 | P1 연결 필요 | `recommendedDefaultFilterId`: 레퍼런스 → 세션 → 온보딩 → 원본 |
| 레퍼런스 색감 재현 품질 평가 | 미구현 | 미판정 | 필터 수치 변환만으로는 특정 사진의 분위기 재현을 보장하지 않음 |

기본 6종 프리셋은 내 감도 생성 후에도 유지된다. `구도만` 레퍼런스는 결과 색감 항목에 추가하지
않지만 기본 필터 목록은 유지한다. 다음 제품 단계에서는 사용자가 선택한 현재 감도(시스템 추천 또는
내 감도)를 결과 화면의 **기본 미리보기**로 먼저 렌더링하고, 원본·다른 필터는 비교 선택지로
내려야 한다.

## 8. AI 3 — 감도 맞춤 사진 살리기

### 8.1 공통 흐름

```text
앨범 사진 선택
→ AI로 보정
→ CAMP-2 진단
→ 최대 3개 추천
→ 사용자가 작업 선택
→ 실행 버튼
→ edit-job 생성·폴링
→ 검증된 후보 비교
→ 새 파일 저장
```

- 앱 촬영 사진과 일반 기기 사진을 모두 지원한다.
- 추천 확인만으로 edit-job을 생성하지 않는다.
- 생성 실패 시 원본·로컬 보정은 유지한다.
- 현재 `ResultScreen`과 `RescueSheet`에 UI 흐름이 연결돼 있으나 최신 GPU 세 기능을 포함한 실기기 저장 흐름은 재검증이 필요하다.
- 현재 실기기 보고 기준으로는 AI 보정이 생성 결과를 안정적으로 보여주지 못했으므로, 이 흐름을
  “사용 가능”으로 판정하지 않는다. 서버의 공개 job 성공은 앱 사용자 흐름 성공을 뜻하지 않는다.

### 8.2 작업별 상태

| 작업 | 모델·공급자 | 서버 상태 | 검증 상태 |
|---|---|---|---|
| 내 감도로 정리 | Android 로컬 필터 | 구현 | 사용 가능 |
| 방해 요소 지우기 | LaMa·ComfyUI | 배포 완료 | 실제 후보 2개·공개 job 완료 |
| 여백·화각 확장 | FLUX.1 Fill·ComfyUI | 배포 완료 | 원본 내부 픽셀 보존·공개 job 완료 |
| 역광·광원 재구성 | IC-Light 격리 서비스 | 배포 완료 | 실제 후보·VRAM 반환 확인 |
| 제한적 시점 변경 | ViewCrafter_16 격리 서비스 | 배포 완료 | 후보 2개 `validation=passed` |

공개 `/api/v1/rescue/analyze`의 readiness 기반 capability는 현재 `localStyle`, `removeObjects`, `outpaint`, `relight`, `viewpoint` 모두 `true`다.

### 8.3 생성 작업 제한과 현재 화면 한계

- outpaint: `all/top/bottom/left/right`, 5·10·15%
- viewpoint: `left/right/up/down/dolly_out`, `subtle/standard`
- relight: `front/left/right`
- remove_objects: 명시적 마스크만
- 한 edit-job에는 생성 operation 하나만 허용한다.
- 후보가 무결성·크기·원본 보존 검증을 통과하지 못하면 앱에 반환하지 않는다.
- ViewCrafter는 후보당 약 2분이며 후보 2개 작업은 약 5분이 걸릴 수 있다.
- `viewpoint` API는 `left/right/up/down/dolly_out` 및 `subtle/standard` 파라미터를
  받지만, 현재 Rescue 화면은 이를 사용자가 명시적으로 고르는 UX로 연결하지 않았다.
- 현재 추천 카드의 `보는 위치 바꾸기`는 사용자 의도·방향을 설명하거나 고르게 하지 않으므로
  완성 기능으로 취급하지 않는다. 임의 시점 변경 결과는 노출하지 않는다.

### 8.4 목표 AI 보정 흐름 (미구현 제품 계약)

```text
사진 촬영 또는 앨범 선택
→ 현재 내 감도의 로컬 보정 결과를 기본으로 표시
→ 원본과 비교·저장
→ 사진이 아쉬울 때만 사진 살리기 선택
→ AI가 가능한 복구를 제안
→ 사용자가 화각/여백 방향, 시점 방향·강도, 조명 의도를 선택
→ 명시적 실행
→ 검증된 후보와 기본 보정 비교·새 파일 저장
```

- **기본 보정:** 사용자 취향이 우선이며, 객체 삭제는 기본 추천이 아니다.
- **화각·여백:** `더 넓게`, `위/아래/왼쪽/오른쪽`과 5·10·15%처럼 사용자가 범위를 고른다.
- **시점:** `왼쪽에서`, `오른쪽에서`, `조금 위에서`, `더 멀리서`와 약한/기본 강도를 고른다.
  사진 한 장에서 실제 카메라 위치를 정확히 복원하는 기능이라고 약속하지 않는다.
- **조명:** 단순 밝기 증가가 아니라 `역광 인물 밝게`, `창가 분위기 유지`처럼 결과 의도를 고른다.
- **노출 정책:** provider readiness와 실기기 성공이 모두 확인된 작업만 노출한다. 실패·미배치·품질
  미달 작업은 숨기고, 원본과 내 감도 로컬 보정은 항상 유지한다.

### 8.5 지금의 감도로 다시 — P2 통합 브랜치 추가

P2는 기존 Rescue 진단을 현재 사용자 감도 정책과 재해석 수준을 받는 계약으로 확장했다. 이 변화는
생성 도구를 나열하는 것이 아니라, 현재의 감도로 사진을 다시 보게 하는 흐름을 만들기 위한 기반이다.

| 기능 | 구현 상태 | 사용자 상태 | P2 코드·연결 정보 |
|---|---|---|---|
| 재해석 수준 | P2 코어 완료 | P1 UI 필요 | `data/rescue/RescueContext.kt`: `MEMORY`, `GAMDO`, `REIMAGINE` |
| 현재 감도 정책 전달 | P2 코어 완료 | P1 연결 필요 | `RescueRepository.analyze(..., RescueContext)`, 서버 multipart `profileVersion`, `sceneContext`, `gamdoPolicy` |
| MEMORY 로컬 경로 | 구현 | P1 UI 필요 | 생성 job 없이 로컬 보정만 반환해야 함 |
| GAMDO·REIMAGINE 진단 | P2 코어 완료 | P1 실행 UI 필요 | `/api/v1/rescue/analyze`가 readiness와 추천을 반환 |
| 화각·시점·조명 작업 파라미터 | 서버·Android 계약 구현 | P1 선택 UI 필요 | outpaint 방향/비율, viewpoint 방향/강도, relight 방향 |
| 결과 기본값·필터 분리 | P2 코어 완료 | P1 구독 필요 | `ResultFilterStateHolder`는 렌더 실패와 목록 상태를 분리 |

기존 화면의 `AI로 보정`은 여전히 이 새 `RescueContext`를 완전히 전달·표현하지 않는다. 따라서
P1이 `MEMORY → GAMDO → REIMAGINE` 선택, 작업 파라미터 확인, 실행 전후 비교를 연결하기 전에는
AI 3을 사용자 완성 기능으로 판정하지 않는다.

### 14.1 P1 요청을 막지 않기 위해 남은 P2 연결 어댑터

아래는 화면 디자인이 아니라 P1이 공개 계약을 안전하게 호출하기 위해 P2가 다음 작업에서 먼저
제공해야 할 작은 연결 계층이다. P1 요청서에도 이 전제를 기록했다.

| P2 보강 항목 | 현재 사실 | 필요한 결과 |
|---|---|---|
| 영역 선택 ViewModel 어댑터 | `SceneGuideSessionController`에는 `rescanInPolygon()`·`cancelPolygonSearch()`가 있으나 `CameraViewModel` 공개 함수는 없음 | 분석 스레드 안전성을 유지하는 `CameraViewModel` wrapper와 `searchScope` 공개 |
| 상황별 카메라 정책 적용 | `GamdoProfileV2.toCameraStyleTarget()`은 구현됐지만 호출자는 아직 없음 | 카메라 진입/장면 변화에서 `SceneContextResolver` 결과를 현재 `StyleTarget`에 반영 |
| 결과 필터 상태 실제 소비 | holder는 `AppContainer`에 등록됐지만 기존 `ResultScreen`은 직접 목록을 구성 | P1이 holder를 구독할 수 있는 ViewModel 상태 또는 화면 연결 |
| Rescue 상황별 정책 실제 전달 | `RescueContext`·서버 multipart는 구현됐지만 기존 화면은 기본값으로 호출 | 현재 프로필·사진 맥락·선택 수준을 만드는 UI-facing factory |
| QR 세션 polling facade | API client는 `getShootSession()`을 제공하지만 repository는 local `active()`만 제공 | repository `refresh/poll` StateFlow와 수신 전 사진 수 상태 |

이 다섯 항목은 “P1이 디자인을 덜 했기 때문”이 아니라, 현재 P2 코어가 아직 UI 경계까지 완결되지
않았다는 뜻이다. 다음 P2 작업에서 우선 처리하며, 그 전에는 P1이 내부 객체나 네트워크 client를
직접 참조하지 않는다.
