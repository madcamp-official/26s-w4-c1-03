## 결함 2 — `내 감도로 정리하기`를 눌러도 아무 변화가 없다

**현재 사용자 막힘 (원인)**

추측이 아니라 코드 경로다. 카드는 `onKeepLocal`을 candidates 섹션과 **공유**하고
있었고, 그 핸들러는 시트를 닫고 controller를 `reset()`하고 `selected_result_id`를
비우는 것이 전부였다. 비트맵을 만드는 코드가 경로 어디에도 없었다. 즉 이것은
회귀가 아니라 **처음부터 no-op로 구현된 계약**이다 —
`P2_통합구현_진행상태_2026-07-29.md:57`이 "이미 표시 중인 로컬 보정 결과를 유지하는
계약"이라고 명시하고 있고, `RescueFlowDecisions.kt`의 `LOCAL_STYLE` 주석도 같은 말을
한다. 브리프 §8이 요구하는 "실행 즉시 전후 변화·저장 가능"은 그 위에 새로 얹힌
요구사항이었고, 구현한 커밋이 없었다.

**조치**

`onApplyLocalStyle`을 `onKeepLocal`에서 분리하고
`selectStrip(localStyleFilterId(filterState))`에 연결했다. 새 렌더링 경로를 만들지
않았다 — 스트립 선택은 프리뷰 루프(`PreviewRequest`)와 `performSave`가 이미 키로
쓰는 자리라, 한 번의 선택으로 `LocalEditor.plan(applyStyle=true)`가 돌고 화면이
바뀌고 전체 해상도 저장까지 그대로 이어진다.

적용 대상은 `ResultFilterState.recommendedDefaultFilterId`다. `내 감도`는 레퍼런스
슬롯의 동의어가 아니라 브리프 §7의 우선순위(활성 레퍼런스 색감 → 촬영 세션 스타일 →
온보딩 추천 → 원본)이고, 그 답을 이미 holder가 들고 있다. **브리프 §7이
"코어 구현, P1 연결 필요"로 적어 둔 `recommendedDefaultFilterId`의 소비처가 이것이다.**
덕분에 레퍼런스를 만든 적 없는 사용자도 자기 감도(세션/온보딩 프리셋)를 적용받는다.

**정답인 no-op 문제**

앱 촬영본은 세션 프리셋으로 열리므로(`ACTIVE_REFERENCE_OPENS_APP_CAPTURES = false`),
레퍼런스가 없는 사용자는 **이미 그 감도가 적용된 상태**에서 카드를 누른다. 이때
아무것도 안 바뀌는 것이 정답이지만, 화면에서 정답인 no-op와 결함은 구분되지 않는다.
그래서 `localStyleChangesPhoto()`로 판정해 `이미 내 감도로 정리돼 있어요`라고 상태를
말하고 버튼을 `확인`으로 바꾼다. 침묵 대신 답을 준다.

**완료 판정 (실기기 — 완료)**

SM-G970N에서 앨범 → 사진 → AI로 보정 → 사진 살펴보기 → 내 감도로 정리하기를
두 경우 모두 확인했다.
- 스트립이 `원본`일 때: 확인 문구 `내 감도로 정리할게요` / 버튼 `적용하기` → 누르면
  배지가 `원본` → `캐주얼 인물`로 바뀌고 사진이 실제로 바뀐다. 스트립 7종 유지, 저장 가능.
- 스트립이 이미 `캐주얼 인물`일 때: `이미 내 감도로 정리돼 있어요` / `확인`.

## 결함 3 — 내 감도를 선택하면 필터 목록·사진이 사라진다

**현재 사용자 막힘 (원인 — 셋이고, holder는 그중 하나도 아니다)**

먼저 확인 사항: `ResultFilterStateHolder` 단일 원천화는 **옳게 되어 있었고 원인이
아니었다.** `items`는 `LocalFilter.entries`(7개 상수)에서 매번 다시 만들어지고,
`select()`·`renderFailed()`는 `items`를 건드리지 않는다. 목록이 빌 수 있는 코드
경로는 존재하지 않는다. 그래서 그 수정 뒤에도 재발한 것이다 — 다른 것을 고치고
있었다.

실제 원인 셋:

1. **58dp 썸네일 안의 15dp `×` 배지.** Compose는 안쪽부터 히트 테스트하므로, 타일
   오른쪽 위 모서리에 손가락이 닿으면 `onSelect`가 아니라 `onDelete`가 실행된다.
   `onDelete`는 `clearActive()` → Room에서 레퍼런스 삭제 → `synchronizeReference(null)`
   → **카탈로그에서 내 감도 항목 제거**다. 확인도 되돌리기도 없고, 앱을 껐다 켜도
   돌아오지 않는다. 사용자 시점에서 이것은 정확히 "내 감도를 눌렀더니 목록에서
   사라졌다"로 보인다. 런타임에 내 감도가 목록에서 빠질 수 있는 유일한 경로다.
2. **decode가 자기 `runCatching` 밖에 있었다.** `passes`가 `produceState`의 키이고
   `style` 플래그는 레퍼런스 슬롯에서만 참이므로, **재decode를 유발하는 스트립 탭은
   내 감도 하나뿐**이다. null이면 `OpenedPhoto.Unavailable` → "사진을 열지
   못했어요"에서 멈추고, `OutOfMemoryError`면 `Error`라서 아무 가드에도 안 걸리고
   Recomposer째 화면이 사라진다. 그 탭은 이 화면의 메모리 최대 지점이기도 하다
   (이전 `corrected`·이전 `edited`·렌더 루프 scratch·새 measure 버퍼가 동시 생존, 회수 없음).
3. **`openTool`이 `remember`였다.** 스트립은 이 시트 안에만 마운트되므로 구성 변경
   (회전, 폰트/다크모드, 메모리 압박 후 OS 재생성) 한 번에 목록이 화면에서 없어진다.
   2번이 메모리 압박을 만들기 때문에 2와 3은 겹쳐서 발생한다.

**조치**

1. 배지 탭 → `onSelect`, 롱프레스 → `onDelete`. 배지를 48dp로 키우는 것은 오히려
   오탭을 늘린다(파괴적 타깃이 조준 대상 **안**에 있다). 롱프레스는 이 화면이 이미
   쓰는 파괴/특수 동작 관용구다(`길게 누르면 원본이 보여요`). 슬롯은 단일이고 `+`로
   덮어쓰므로 삭제는 드문 경로라 강등해도 잃는 것이 없다. `ResultScreen`(58dp)과
   `CameraScreen`(52dp) 양쪽에 적용된다.
2. decode와 `measure`를 `runCatching`(= `Throwable`) 안으로 넣고, **재**decode 실패는
   화면에 있던 비트맵을 유지한다. `Unavailable`은 첫 decode 실패에만 남긴다 — 한 번
   열린 사진에 "열지 못했어요"는 거짓말이다.
3. `openTool`을 `rememberSaveable`로 바꿨다.

**덤: 앱 재시작 복원 (브리프 D-1 6, §5 "앱 재시작 복원 UX")**

`styleChosenByUser` 플래그가 그것이 가리키는 `selectedId`보다 오래 살고 있었다.
holder는 앱 스코프라 회전은 견디지만 프로세스 사망은 못 견딘다. 그래서 콜드 스타트
후 복원된 "사용자가 골랐다"(true)가 `원본`으로 재생성된 holder 위에 얹혀
`selectionOnOpen`이 `원본`을 답하고, **복원된 플래그가
`recommendedDefaultFilterId`를 적극적으로 막고 있었다.** 플래그 대신 고른 id를
저장하도록 바꿨다. 회전은 이미 선택된 것을 다시 선택하고, 콜드 스타트는 holder가
모르는 것을 다시 선택한다.

**완료 판정 (실기기 — 부분)**

스트립 7종 유지·필터 렌더는 기기에서 확인했다. 남은 항목은 **레퍼런스가 활성인
상태**의 회귀 확인이다 (오탭해도 안 지워지는지, 롱프레스로는 지워지는지, 재시작 후
내 감도가 복원되는지). 현재 테스트 기기에 활성 레퍼런스가 없어 P1이 아직 못 돌렸다.

## 결함 5 — AI 후보가 도착했는지, 무엇을 고를지, 저장됐는지 알기 어렵다

**현재 사용자 막힘 (원인)**

`5233bbb` 이후 시트를 치워도 job이 살아남는다. 그런데 `RescueSheet` 밖에서
`rescueState`를 읽는 composable이 **하나도 없다.** 그래서 controller가
`Polling → Candidates`로 가도 화면은 아무 말을 안 한다: 후보는 다운로드되고
`edit_results_local`에 기록되고 열려 있지 않은 시트에 그려진다. `LocalFallback`도
똑같이 조용히 사라진다. 이전 동작은 최소한 시끄럽게 끝났다(job을 죽였다). 알려 주지
않고 살아남는 것은 그보다 나쁘다 — 알려 주지 않은 결과는 결과가 없는 것과 같다.

두 번째로, 후보 섹션의 1차 버튼이 `완료`(= `onClose`, 닫기만)였다. 계약의
`후보 비교 → 새 파일 저장`이 한 단계 일찍 끝나고, 사용자는 시트가 가리고 있던
헤더의 저장 pill을 스스로 찾아야 했다.

**조치**

- `reopensOnOutcome(previous, current, opened)` — running → outcome **엣지**에서만
  시트를 되돌린다. 상태가 아니라 엣지인 것이 핵심이다: 끝난 시트를 닫으면 controller는
  같은 outcome에 머물러 있으므로 두 번째 엣지가 없고, 사용자는 한 번만 닫으면 된다.
  다른 사진의 결과를 든 채 화면에 들어와도 엣지가 없어 열리지 않는다. 취소는 `Idle`이라
  조용하다(사용자가 이미 안다).
- 후보 섹션 1차 동작을 실제 저장(`performSave`)으로 바꾸고, 후보를 고르기 전에는
  비활성이다(고르지 않은 채 저장하면 로컬 보정 결과를 후보인 척 저장하게 된다).
  시트가 가리고 있던 저장 중·저장됨·실패를 시트 안에서도 말한다.

**완료 판정 (실기기 — 실패 경로 확인 완료, 성공 경로 미확인)**

실제 `outpaint` job을 SM-G970N에서 제출해 끝까지 돌렸다.

```
23:24:23  editJobSubmitted capture=true operation="outpaint"
23:24:26  editJobPolling
          ← 여기서 시트를 치움(바깥 탭). job은 계속 살아 있음
23:29:26  editJobFailed  java.lang.IllegalStateException: edit_job_timeout
23:29:26  rescueSheetReopened outcome=LocalFallback     ← 수정이 동작한 지점
```

**시트가 스스로 돌아와 실패를 알렸다.** 수정 전이라면 사용자가 자리를 뜬 뒤 5분 만에
job이 실패하고, 화면은 그 사실을 영원히 말하지 않았을 경로다. 복귀한 시트는
`자연스러운 보정만 적용했어요 / 지금은 AI 보정을 쓸 수 없어서 원래 보정 결과를 그대로
두었어요 / 닫기`를 보여줬고, 닫은 뒤 사진·감도 배지(`캐주얼 인물`)·필터 스트립 7종·
저장 pill이 모두 그대로였다. 브리프 §8의 "실패해도 원본·로컬 보정·저장 경로 유지"가
지켜진다.

엣지 설계도 함께 검증됐다: `rescueSheetReopened` 로그는 **정확히 1회**만 찍혔고, 닫은
시트는 닫힌 채로 남았다. 상태 기반이었다면 여기서 사용자가 시트를 닫을 수 없었다.
크래시 0건.

**남은 것**: 후보가 실제로 도착하는 성공 경로(도착 → 비교 → 선택 → 저장)는 GPU가
5분 예산 안에 결과를 내지 못해 확인하지 못했다. 실패 사유가 `edit_job_timeout`이므로
이것은 앱이 아니라 CAMP-2 가용성 문제다 — **P2에 확인을 요청한다.** 지금 상태로
시연하면 AI 생성 작업은 후보 없이 폴백만 나온다.

**남은 갭 (미조치, P1 판단 필요)**

- **비교 UI 없음.** `CandidatesSection`은 후보 타일만 그린다. 원본 타일도 현재 감도
  타일도 없다. 브리프 §8의 `원본·현재 감도·AI 후보 비교`는 아직 미구현이다.
- **후보를 고르면 `길게 누르면 원본이 보여요`가 원본이 아니라 후보를 보여준다.**
  `source`가 `editSource`에서 파생되고 `editSource`는 후보 파일이기 때문이다. 진짜
  원본에 도달할 방법이 화면에서 사라진다.
- **진행 표시에 단계·경과가 없다.** `EditJobStatus.status`/`progressStage`는 와이어로
  도착하는데 `submitAndPoll`의 루프가 읽고 버린다. `onPolling`은 루프 **앞에서** 한 번만
  불린다. 그래서 최대 5분(`JobTimeoutPolicy.BUDGET`) 동안 변하지 않는 스피너 하나다.
  이걸 고치려면 `onPolling`이 `EditJobStatus`를 받도록 넓히고 `RescueState.Polling`이
  값을 싣게 해야 하는데, 둘 다 `data/rescue/`라 **P2 소유**다. P2 판단을 요청한다.

## 결함 1·4 — P2 소유 항목에 대한 P1 관측

- **결함 1 (올가미).** P1 조치 없음. 영역 선택 모드·경로 수집·제출·취소의 화면 연결은
  이미 되어 있고(`AreaSelectPath.kt`, `AreaSelectGesture.kt`), 앵커 클러스터 제거 수정
  이후의 재검증은 P2 항목이다.
- **결함 4 (레퍼런스 색감 과포화).** P1 조치 없음. 다만 브리프 §6 C-1이 P1에게 물은
  "어떻게 비교하면 과포화를 즉시 발견할 수 있는가"에 대해: 현재 화면에 이미
  `길게 누르면 원본이 보여요`가 있고 이것이 그 비교 도구다. 내 감도 적용 상태에서
  길게 누르면 감도 없는 사진이 나오므로 과포화는 즉시 보인다. **단 위에 적은 대로 AI
  후보를 고른 뒤에는 이 비교가 깨진다.** 색감 파라미터 자체(과채도·과대비)는 P2 영역이다.

## 결함 6 — 코어는 있으나 화면에서 진입할 수 없는 기능

브리프 작성 시점 기준으로 재확인한 결과, 셋 중 둘은 **이미 연결되어 있다.**

| 기능 | 상태 | 근거 |
|---|---|---|
| 수동 프레임 12종 | 연결됨 | `ui/camera/ManualFrameSelection.kt` + `ManualFrameSelectionTest` |
| 인물/물체 슬롯 `visualKind` | 연결됨 | `ui/camera/SlotRenderStyle.kt` + `SlotRenderStyleTest` |
| 영역 선택(올가미) | 연결됨 | `AreaSelectPath.kt` + `AreaSelectPathTest` |
| AI 직접 수정 | 연결됨 | `ui/rescue/DirectEditPane.kt` (기기에서 `직접 고르기` 확인) |
| QR 나 찍어줘 | **미연결(의도적)** | 아래 |

**QR 미노출 사유 — 코드 주석의 근거는 만료됐다. 실제 원인은 다르다**

`Routes.kt`의 `SHOOT` 주석은 "`gamdo-web/dist`가 없어 서버가 `/shoot/{token}`에 503을
준다"고 적고 있다. **실측해 보니 사실이 아니다.**

```
GET https://api.anjonghwa.madcamp-kaist.org/shoot/testtoken   → 200
   본문: Vite 빌드 index.html (React 앱, 해시 에셋 참조)
```

웹은 배포돼 있다. 로컬 체크아웃에 `gamdo-web/dist`가 없을 뿐이고, 그것은 서버가 아니라
내 작업 트리의 상태다. 주석은 그때는 맞았고 지금은 아니다.

**그런데 흐름은 여전히 깨져 있고, 원인은 경로 한 조각이다.**

서버가 내려주는 `index.html`은 다음을 참조한다.

```html
<script type="module" src="/web-assets/assets/index-Bl7vDHnZ.js"></script>
<link rel="stylesheet" href="/web-assets/assets/index-CQrNzL6z.css">
```

그런데 `gamdo-server/app/main.py:34`는 이렇게 마운트한다.

```python
app.mount("/web-assets", StaticFiles(directory=str(WEB_DIST / "assets")), name="web-assets")
```

`assets` **디렉터리 자체**를 `/web-assets`에 붙였으므로 실제 URL에는 `assets/`가 한 번만
들어가야 한다. 실측이 그대로 확인해 준다.

```
/web-assets/assets/index-Bl7vDHnZ.js  → 404   ← index.html이 부르는 주소
/web-assets/index-Bl7vDHnZ.js         → 200   ← 실제로 있는 주소
```

즉 친구가 QR 링크를 열면 **503이 아니라 흰 화면**을 본다. HTML은 오지만 JS/CSS가 404라
React가 마운트되지 않는다.

**P2에 요청 (서버·웹 소유)**: 한 줄이다. `main.py:34`를 `WEB_DIST`로 마운트하거나, Vite
`base`를 에셋이 평평하게 떨어지도록 맞추면 된다. 어느 쪽이 맞는지는 P2 판단이다. P1은
`gamdo-server`를 수정하지 않는다.

**P1 쪽 상태**: `DelegatedShootScreen`·`DelegatedShootController`·`ShootQrCode`·
`GamdoNavHost` 라우트·`onOpenDelegatedShoot`가 모두 준비돼 있고, 남은 것은 카메라
보조 액션에서 이를 호출하는 것뿐이다(6bef31b가 요구한 형태). 위 경로 수정 없이 먼저
노출하면 QR은 만들어지지만 친구 쪽이 흰 화면이므로, **노출 시점은 오너 판단으로 남긴다.**
