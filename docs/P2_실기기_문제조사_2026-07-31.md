# P2 실기기 문제 조사 보고서 — 2026-07-31

## 조사 범위

이번 기록은 수정 없이 현재 `main`의 앱과 연결 기기 로그를 조사한 결과다. 대상은 다음 사용자 제보 다섯 가지다.

1. 카메라 사용 중 앱이 종료됨
2. 하단 고정 인물 레이아웃이 작동하지 않음
3. 레이아웃 표시 모양이 네모와 동그라미로 섞임
4. 인물 레이아웃의 사용 방법이 불명확함
5. 객체 인식률을 확인할 수 없음

현재 기준 커밋은 `87c0971`이다. 연결 기기에서 패키지 `com.gamdo.app`의 PID `24933` 로그를 확인했다.

## 1. 앱 종료/크래시

### 확인된 사실

최근 로그에서 앱 분석 로그는 다음과 같이 반복됐다.

```text
DetectStage: face=약 50~60ms pose=0.0 seg=0.0 obj=0.0 post=0.0
             segRun=false objRun=false segNonNull=false
CameraScreen: faces=0 no-face
```

이후 `pidof com.gamdo.app`가 빈 결과를 반환해 해당 프로세스가 더 이상 실행 중이 아닌 상태는 확인됐다. 그러나 보존된 ADB 로그 범위에서는 다음 치명적 종료 표식이 확인되지 않았다.

- `FATAL EXCEPTION`
- `AndroidRuntime`
- `Fatal signal`
- `SIGSEGV`
- `Process: com.gamdo.app`

### 판정

현재 자료만으로는 Kotlin 예외, native SIGSEGV, 사용자의 뒤로가기·카메라 종료, 시스템 프로세스 회수 중 무엇인지 확정할 수 없다. 따라서 “크래시 원인 해결 완료”로 기록할 수 없다.

다만 객체·분할 단계에서 native 오류가 발생했다는 직접 증거도 이번 로그에는 없다. `segRun=false`가 계속 기록되어 분할기가 실행된 뒤 죽은 상황으로 판단할 근거가 없다.

### 추가로 필요한 재현 증거

크래시를 다시 재현할 때 앱 실행 직전부터 다음을 별도 수집해야 한다.

```powershell
adb logcat -c
adb logcat -v threadtime > gamdo-crash.log
# 앱 실행 → 카메라 진입 → 크래시 재현
adb shell dumpsys dropbox --print system_app_crash
```

로그를 지우는 `logcat -c`는 이번 조사에서는 실행하지 않았다. 다음 재현에서만 사용해야 하며, `AndroidRuntime` 또는 `Fatal signal`의 첫 stack frame이 원인 확정 기준이다.

## 2. 고정 레이아웃이 작동하지 않는 문제

### 코드상 확인된 경로

하단 목록은 `LayoutTemplateCatalog.manualSummaries`에서 생성된다.

현재 인물 ID와 표시 이름은 다음처럼 존재한다.

| ID | 표시 이름 | `resolve()` 결과 |
|---|---|---|
| `person_full_center_v2` | 전신 중앙 | `PERSON_BRACKET` 한 슬롯 |
| `person_full_offset_v2` | 전신 비대칭 | `PERSON_BRACKET` 한 슬롯 |
| `person_full_relaxed_v3` | 전신 자연스러운 흐름 | `PERSON_BRACKET` 한 슬롯 |
| `person_full_walking_v3` | 전신 리드 룸 | `PERSON_BRACKET` 한 슬롯 |
| `person_upper_v2` | 상반신 | `PERSON_BRACKET` 한 슬롯 |
| `person_seated_v2` | 앉은 인물 | `PERSON_BRACKET` 한 슬롯 |

선택 이벤트는 `CameraScreen → CameraViewModel.selectManualLayout() → pendingGuideWork → SceneGuideSessionController.selectManualLayout() → SceneGuideCoordinator.selectManualLayout()` 순서로 지연 실행된다.

### 문제로 확인되는 설계 취약점

- `CameraViewModel.selectManualLayout()`은 즉시 적용하지 않고 분석 스레드의 `pendingGuideWork`에 넣는다. 사용자가 누른 순간 화면 상태가 바뀌지 않아 “버튼이 작동하지 않는다”처럼 보일 수 있다.
- 수동 선택 직후 현재 레이아웃을 렌더링하는 상태 전달은 `layoutState`와 `layoutGuide.fixedLayout` 두 경로에 의존한다. 어느 한쪽이 갱신되지 않으면 선택은 성공해도 오버레이가 보이지 않는다.
- `CameraOverlay`는 `data.layoutGuide?.fixedLayout`이 있을 때만 수동 템플릿을 그린다. 수동 선택 결과가 `GuideLayoutState.Fixed`에만 들어가고 `layoutGuide.fixedLayout`에 들어가지 않는 경우, 실제 캔버스에는 아무것도 그리지 않는다.
- 인물 수동 템플릿은 모두 `PERSON_BRACKET`이므로 자동 인물 장면에서 사용되는 `PERSON_SILHOUETTE`와 시각적으로 다르다. 사용자는 같은 “인물 레이아웃”으로 기대하지만 코드상 서로 다른 렌더 경로다.

### 판정

레이아웃 ID와 템플릿 자체는 존재한다. 따라서 카탈로그가 비어 있는 문제가 아니다. 현재 증상은 **수동 선택 이벤트의 지연 적용 또는 `layoutState`와 `layoutGuide.fixedLayout` 사이의 연결 불일치**를 우선 의심해야 한다. 이번 조사는 실제 버튼 클릭 시점의 상태 전이를 수집하지 않았으므로 단일 원인으로 확정하지 않는다.

## 3. 네모와 동그라미가 섞이는 문제

현재 렌더러는 슬롯의 `visualKind`에 따라 의도적으로 세 가지 스타일을 선택한다.

| 슬롯 시각 종류 | 렌더 스타일 | 표시 형태 |
|---|---|---|
| `PERSON_SILHOUETTE` | 사람 실루엣 | 머리 원 + 몸 윤곽 + 발 마커 |
| `PERSON_BRACKET` | 인물 브래킷 | 네 모서리 + 머리 위치 원 |
| `GENERIC_OBJECT`, `CUP`, `PLATE` | 객체 브래킷 | 네 모서리 |

따라서 네모와 동그라미가 섞이는 것은 랜덤 렌더 오류가 아니라 `SlotRenderStyle.of()`의 계약 결과다. 문제는 이 계약이 사용자에게 설명되지 않고, 같은 인물 기능에서도 자동 레이아웃은 실루엣, 수동 레이아웃은 브래킷을 사용한다는 점이다.

### 판정

기술적으로는 슬롯 종류별 구분이 있으나, 제품 경험 기준으로는 시각 언어가 통일되지 않았다. 특히 사람을 어떻게 맞추는지 설명하는 핵심 요소가 `PERSON_BRACKET`의 작은 머리 원 하나에 의존해 사용자에게 의미가 전달되지 않는다.

## 4. 인물 레이아웃 사용 방법이 불명확한 이유

현재 수동 인물 템플릿은 다음 정규화 영역만 제공한다.

```text
전신 중앙:       x 0.30~0.70, y 0.08~0.94
전신 비대칭:     x 0.15~0.53, y 0.08~0.94
자연스러운 흐름: x 0.27~0.72, y 0.08~0.94
리드 룸:         x 0.14~0.55, y 0.08~0.94
상반신:          x 0.30~0.78, y 0.17~0.92
앉은 인물:      x 0.20~0.80, y 0.15~0.90
```

하지만 제품 경로에는 다음 정보가 없다.

- 머리·발·어깨 등 사용자가 맞춰야 할 시각적 기준의 명확한 구분
- 현재 인물이 목표 영역에 들어왔는지 여부를 알려주는 제품 상태
- “전신 비대칭”과 “전신 자연스러운 흐름”의 차이를 보여주는 설명
- 앉은 인물에서 좌석과 하체를 어떻게 포함해야 하는지에 대한 시각적 의미

또한 자동 장면과 수동 목록의 인물 표현이 다르다. 자동 경로는 `PERSON_SILHOUETTE`가 될 수 있지만, 수동 인물 목록은 모두 `PERSON_BRACKET`이다. 사용자가 하단 레이아웃을 선택해도 실루엣이 아니라 사각 브래킷과 작은 원만 보이는 이유가 여기에 있다.

### 판정

현재 인물 레이아웃은 “사용자가 직접 움직여 고정 가이드에 맞춘다”는 계약의 데이터는 있으나, 실제 촬영자가 해석할 수 있는 시각적 안내 수준은 부족하다. 이는 인식 실패라기보다 **프레이밍 템플릿과 렌더 표현 사이의 의미 손실**이다.

## 5. 객체 인식률을 확인할 수 없는 문제

### 현재 로그가 제공하는 것

현재 Debug 로그/HUD에는 상황에 따라 다음 값이 있다.

- 분석 시간
- FPS 및 프레임 드롭
- 얼굴 수
- 원시 객체 수와 일부 라벨·confidence
- `objRun`, `segRun` 실행 여부
- `layout=detecting/confident` 또는 고정 템플릿

### 현재 로그가 제공하지 않는 것

- 실제 장면의 정답 객체 수
- 객체별 true positive / false positive / false negative
- 같은 객체의 중복 검출률
- 올가미 내부 recall과 외부 오포함률
- 겹친 물체 분리 성공 여부
- 자동 고정까지의 장면별 시간 분포
- 수동 판정 객체 수와 슬롯 수의 일치율

이번 로그에서도 다수의 프레임이 `objRun=false`였고, 객체 단계 시간이 `0.0ms`였다. 이 프레임들은 객체 인식률을 평가할 수 있는 추론 결과가 아니라, 객체 detector가 실행되지 않은 분석 프레임이다. 따라서 HUD의 “물체 수”가 있더라도 그것만으로 모델 recall을 계산할 수 없다.

### 판정

현재 앱에는 “인식률”이라는 단일 사용자 확인 지표가 구현되어 있지 않다. 정확도를 말하려면 촬영 장면별 사람이 기록한 정답 목록과 앱 후보 목록을 비교해야 한다. 실기기 로그만으로는 처리 성능은 볼 수 있지만 정확도는 증명할 수 없다.
